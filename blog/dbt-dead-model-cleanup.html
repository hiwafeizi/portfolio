Finding 5,000 dead tables in a 10,000-model warehouse

After a multi-year migration our platform had over 10,000 models in code and even more objects deployed, and everyone suspected a lot of it was dead. Nobody would delete anything without proof. This is the method that produced the proof, and it isn't specific to any tool: it needs a warehouse catalog, a transformation codebase, and a repo you can search. The dbt + Snowflake specifics are at the end. Names are generic; the methods and numbers are real.

TL;DRDead weight hides in three places: deployed but never declared in code, declared but feeding nothing that matters, and dropped from use but still mentioned somewhere. So: diff the warehouse catalog against the code graph, walk the graph upstream from an opt-in list of needed endpoints, and before deleting anything, grep the entire repo for every candidate's name. Zero references anywhere: ~5,000 tables, retired. One or more mentions: 2,000, queued for deeper review. Nothing is dropped outright: retired means renamed first, deleted months later.

Nobody deletes anything, and that's rational

Deleting in a large warehouse is asymmetric: keeping a dead table costs a little every day (storage, catalog noise, misleading lineage, one more thing every newcomer reads around), but dropping a live one breaks somebody's Monday. Without evidence, the rational move is always to keep it. That's how a platform ends up with thousands of objects nobody can vouch for.

The instinct is to hunt for dead models inside the transformation code. We did find some there, 400 models nothing user-facing consumes anymore. But the real finding was elsewhere: most of the dead weight was not in the code at all. It was objects sitting in the warehouse that the codebase never even mentions: leftovers from migration phases, hand-made backups (_bkp, _old, tmp), experiments, and deployments of models long since deleted. No analysis of the code can find those, because the code doesn't know they exist.

The method: three checks, in order of value

1 · Diff the warehouse against the code graph

Reduce both sides to comparable keys (schema + object name) and set-diff them. Three buckets fall out:

  • In the warehouse, not in the code: the big one. Objects nothing in the codebase even attempts to reference, invisible to every code-level analysis by definition.
  • In the code, not in the warehouse: disabled or never-deployed models; repo hygiene rather than warehouse hygiene.
  • In both, but not necessarily earning its keep: a match only proves the object exists on both sides. Enrich each one with row counts, size, days since last altered, and whether anything needed sits downstream: some turn out untouched for months, and others load fresh data every day into a table nothing needed ever reads. Being loaded and being used are different things.

2 · Opt in what's needed, subtract the rest

Inside the code graph, don't ask "what looks dead?"; ask the opposite. Enumerate the endpoints that are legitimately needed (the user-facing layer, plus every other sink that counts as a real consumer), walk the dependency graph upstream from all of them, and take the closure: everything that directly or indirectly feeds a needed endpoint is alive. Everything outside that closure has to argue for its life. For each candidate, attach its parents, children, and full downstream tree, so the person reviewing sees context, not just a name. This is what surfaced the 400 unconsumed models.

The whole step rests on the opt-in list being right. Miss a legitimate endpoint and the analysis flags living models as dead; that list deserves more care than the graph walk itself.

3 · Before deleting: grep everything

Graph analysis says "probably dead". We wanted provably unreferenced. So the last gate is deliberately dumb: take every candidate's name and search the entire repo for any mention at all, in any file: SQL, YAML, macros, docs, scripts, tests. The split decides the fate:

  • Zero mentions anywhere: provably unreferenced. That was ~5,000 tables, and they were retired.
  • One or more mentions: 2,000 objects that something, somewhere still names. Each needs a human to judge whether the mention is real usage or a stale comment, so they went to a review queue instead of the drop list.

Package it for the person who decides

The analyses produce candidates; people approve drops. So everything lands in one Excel workbook, one row per object with its schema and name spelled out, and the columns a decision actually needs: last altered date on Snowflake, row count, size, days since last change, whether anything needed sits downstream, and where any lingering mentions live. With that in front of a decision maker, the call stops being a debate: sort by last altered, start with objects untouched for nine months or more, and every "are we sure?" has a column that answers it. Clear metadata, clearly explained, is what turns a drop decision from an argument into a filter.

Deliberately not a pipeline

None of this is wired into CI. The scripts are read-only, run one at a time, and their outputs are reviewed by hand before anything is dropped. That's not a missing feature: deletion is the one operation where the process should be slow, boring, and reversible. The tooling's job is to make the candidate list trustworthy and the review easy, not to act. Order of operations for anyone repeating this: the warehouse diff first, the endpoint closure second, and nothing gets dropped without passing the grep gate.

Even retirement itself is soft. Nothing goes straight to DROP: a retired table or view is renamed with a to_be_deleted marker, so any query that still touches it fails loudly while the data stays fully intact and restorable in seconds. Only after a few quiet months do the renamed objects get dropped for real. The rename is the one test no analysis can run: production traffic itself proving that nothing needed the table.

What I learned

  • The biggest dead weight wasn't in the code at all. Objects the codebase never mentions can only be found by diffing the catalog against the graph; no amount of code analysis will surface them.
  • "Needed" is an opt-in list, not a guess. Enumerate the legitimate endpoints and walk upstream; everything else must argue for its life. Getting that list right matters more than the traversal.
  • A dumb grep beats a clever analysis for confidence. Searching the whole repo for every candidate name is crude, and it is exactly what turned "probably dead" into 5,000 provably-unreferenced tables and 2,000 for a human.
  • Metadata makes the decision objective. One workbook with last altered, row count, size, and downstream context per object turns "dare we drop this?" into "filter for untouched for 9+ months and work down the list."
  • Keep deletion human, and soft. Read-only scripts, manual review, and a to_be_deleted rename that waits out a few months of production traffic before the real drop: for destructive cleanup, slow is the design.

The dbt + Snowflake implementation

How each check maps onto our actual stack, folded away so the story stays short.

The code graph: dbt's manifest

Everything on the code side reads target/manifest.json, dbt's compiled project graph:

  • nodes[uid]['depends_on']['nodes']: each model's upstream refs and sources, used to walk the graph in either direction.
  • nodes[uid]['original_file_path']: classifies models by folder layer and detects inactive/ folders.
  • nodes[uid]['schema'] / ['alias'] / ['config']: materialization, tags, enabled flag, and the (schema, alias) key for the warehouse diff.

A model counts as used only if something refs it in dbt; that blindness to undeclared objects is exactly why the warehouse diff runs first.

The warehouse diff against Snowflake

One INFORMATION_SCHEMA extract covers the in-scope schemas (log and metadata schemas excluded). Both sides reduce to (SCHEMA, ALIAS) keys and set-diff into the three buckets. Likely backup and scratch names (_bkp, _backup, _old, test, tmp) get flagged as hints on the orphan list. Matches are enriched with row_count, bytes, created, last_altered, days since altered, and an upstream-of-needed-endpoints flag reusing the closure below. Output lands in one workbook, one tab per bucket, numerics coerced for sorting.

The endpoint closure and lineage workbook

The opt-in endpoint set in our project: every user-facing mart model plus every business-vault model (bv_*). A breadth-first walk over depends_on from all endpoints builds the "alive" closure. For each model outside it, the script records direct upstream and downstream, total downstream closure size, and a nested JSON lineage tree (diamond joins collapse to a leaf name so the tree stays finite). Output is a workbook with one tab per layer, so the reviewer never has to open the manifest.

The grep gate

Every candidate name from the previous two checks is searched across the entire GitHub repository: any file type, any match, case-insensitive. The tally per name (zero vs one-or-more mentions) produces the final split: the zero-mention list is eligible for retirement, the rest goes to the review queue with the mention locations attached. Crude on purpose: the point of this gate is that it cannot be outsmarted by an edge the graph model didn't capture.
